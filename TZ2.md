## 1. Описание проекта

**TaxiService_Itrun** — учебная система управления службой такси.

Программа должна позволять:

- Регистрировать пассажиров.
- Регистрировать водителей и их автомобили.
- Создавать заказы на поездки.
- Рассчитывать стоимость поездки в зависимости от тарифа.
- Принимать заказы водителями.
- Начинать и завершать поездки.
- Отменять заказы.
- Отслеживать занятость водителей.
- Просматривать историю заказов.
- Рассчитывать общую выручку от завершённых поездок.
- Сохранять данные между запусками программы.

Все действия выполняются через консольное меню.

**Главная цель:** продемонстрировать практическое применение ООП в Python при разработке программы, состоящей из нескольких взаимодействующих классов.

## 2. Ограничения проекта

Первая версия разрабатывается исключительно на Python.

Не использовать:

- Django, Flask и FastAPI.
- SQL и другие базы данных.
- HTML, CSS, JavaScript.
- Графический интерфейс.
- Реальные платёжные системы.
- Карты, GPS и геолокацию.
- Настоящую авторизацию пользователей.

Для хранения информации используется JSON.

В проекте необходимо применять стандартную библиотеку Python. Внешние зависимости для основной функциональности не требуются.

## 3. Типы пользователей

### 3.1. Пассажир (Passenger)

Поля:

- `user_id` — уникальный идентификатор пассажира.
- `name` — имя.
- `phone` — номер телефона.

Возможности:

1. Зарегистрироваться.
2. Просмотреть свой профиль.
3. Изменить имя и телефон.
4. Создать заказ.
5. Выбрать тариф.
6. Указать расстояние поездки.
7. Узнать предварительную стоимость.
8. Просмотреть свои заказы.
9. Отменить доступный для отмены заказ.

### 3.2. Водитель (Driver)

Поля:

- `user_id` — уникальный идентификатор водителя.
- `name` — имя.
- `phone` — номер телефона.
- `car` — объект автомобиля.
- `is_available` — доступность водителя.

Возможности:

1. Зарегистрироваться.
2. Указать данные автомобиля.
3. Просмотреть профиль.
4. Изменить свои данные.
5. Просмотреть новые заказы.
6. Принять подходящий заказ.
7. Начать поездку.
8. Завершить поездку.
9. Просмотреть историю выполненных поездок.

Водитель не должен одновременно обслуживать два заказа.

### 3.3. Администратор

Отдельный класс `Admin` в первой версии не требуется.

Вместо него в главном консольном меню реализуется административный раздел для управления пассажирами, водителями, заказами и просмотра статистики.

Настоящую систему авторизации в этом проекте не разрабатываем.

## 4. Основные классы

### 4.1. Абстрактный класс User

Родительский класс для пассажиров и водителей.

Атрибуты:

- `user_id`
- `name`
- `phone`

Методы:

- `get_info()` — абстрактный метод получения информации.
- `update_name(new_name)`
- `update_phone(new_phone)`

Требования:

- Использовать `ABC`.
- Использовать `@abstractmethod`.
- Запретить непосредственное создание объекта абстрактного класса User.
- Реализовать метод `get_info()` в дочерних классах.

### 4.2. Класс Passenger(User)

Наследуется от User.

Должен реализовать:

- Собственный `get_info()`.
- Получение списка заказов пассажира через сервис.

Пассажир не хранит отдельную независимую копию всех заказов. Заказы централизованно хранятся в TaxiService.

### 4.3. Класс Driver(User)

Наследуется от User.

Дополнительные атрибуты:

- `_is_available`
- `car`

Методы:

- `get_info()`
- `mark_busy()`
- `mark_available()`

Для получения статуса доступности использовать `@property`.

Изменять состояние занятости водитель должен через предусмотренные методы и сервисную логику.

### 4.4. Класс Car

Представляет автомобиль водителя.

Атрибуты:

- `brand` — марка.
- `model` — модель.
- `plate_number` — государственный номер.
- `category` — категория автомобиля.

Допустимые категории:

- `standard`
- `comfort`

Метод:

- `get_info()`

Один водитель имеет один автомобиль в первой версии программы.

Автомобиль с одинаковым государственным номером не может быть зарегистрирован у двух водителей.

### 4.5. Абстрактный класс Tariff

Используется для расчёта стоимости поездок.

Метод:

- `calculate_price(distance)` — абстрактный метод.

Дочерние классы самостоятельно определяют формулу расчёта цены.

### 4.6. Класс StandardTariff(Tariff)

Тариф «Стандарт».

Стоимость:

- Посадка: 10 сомони.
- Один километр: 3 сомони.

Формула:

`price = 10 + distance * 3`

Пример:

Расстояние 6 км.

Стоимость: 28 сомони.

### 4.7. Класс ComfortTariff(Tariff)

Тариф «Комфорт».

Стоимость:

- Посадка: 20 сомони.
- Один километр: 5 сомони.

Формула:

`price = 20 + distance * 5`

Пример:

Расстояние 6 км.

Стоимость: 50 сомони.

Оба тарифных класса реализуют метод `calculate_price()`, но с разной логикой.

Это обязательный пример полиморфизма.

### 4.8. Класс Order

Представляет отдельный заказ такси.

Атрибуты:

- `order_id`
- `passenger_id`
- `driver_id`
- `distance`
- `tariff_name`
- `price`
- `status`

В момент создания заказа `driver_id` отсутствует, поскольку заказ ещё не принят водителем.

Методы:

- `get_info()`
- `accept(driver_id)`
- `start_trip()`
- `complete_trip()`
- `cancel()`

Важное условие: методы должны контролировать допустимые переходы между статусами.

### 4.9. Класс TaxiService

Главный класс управления бизнес-логикой.

Хранит:

- Список пассажиров.
- Список водителей.
- Список заказов.

Методы:

- `add_passenger()`
- `add_driver()`
- `find_passenger()`
- `find_driver()`
- `update_passenger()`
- `update_driver()`
- `delete_passenger()`
- `delete_driver()`
- `create_order()`
- `accept_order()`
- `start_trip()`
- `complete_order()`
- `cancel_order()`
- `get_orders()`
- `get_available_drivers()`
- `calculate_total_revenue()`

Методы должны возвращать результаты операций или вызывать понятные исключения.

Методы сервиса не должны самостоятельно запрашивать ввод пользователя через `input()`.

## 5. Логика управления заказами

### 5.1. Создание заказа

Пользователь выбирает пассажира, тариф и указывает расстояние.

Программа:

1. Проверяет существование пассажира.
2. Проверяет корректность расстояния.
3. Проверяет существование тарифа.
4. Рассчитывает стоимость.
5. Генерирует уникальный ID заказа.
6. Создаёт объект Order.
7. Присваивает заказу статус `new`.
8. Добавляет заказ в общий список.
9. Выводит информацию о заказе.

### 5.2. Принятие заказа

Водитель выбирает новый заказ.

Программа должна проверить:

- Существует ли заказ.
- Имеет ли заказ статус `new`.
- Существует ли водитель.
- Свободен ли водитель.
- Соответствует ли категория автомобиля выбранному тарифу.

При успешном принятии:

- Заказ закрепляется за водителем.
- Статус становится `accepted`.
- Водитель становится занятым.

### 5.3. Начало поездки

Начать можно только принятый заказ.

Статус изменяется:

`accepted → in_progress`

### 5.4. Завершение поездки

Завершить можно только начатую поездку.

После завершения:

- Статус заказа меняется на `completed`.
- Водитель становится свободным.
- Сумма заказа учитывается в общей выручке.

### 5.5. Отмена заказа

Допускается отмена заказов со статусами:

- `new`
- `accepted`

Если заказ уже принят, при отмене водитель снова становится доступным.

Отменить начатую или завершённую поездку нельзя.

Стоимость отменённого заказа не учитывается в выручке.

### 5.6. Статусы заказов

| Статус | Значение |
|---|---|
| `new` | Новый заказ |
| `accepted` | Принят водителем |
| `in_progress` | Поездка выполняется |
| `completed` | Завершён |
| `cancelled` | Отменён |

Допустимая последовательность:

`new → accepted → in_progress → completed`

Дополнительные переходы:

`new → cancelled`

`accepted → cancelled`

Повторное завершение или принятие заказа должно быть запрещено.

## 7. Валидация данных

Обязательные проверки:

1. Имя пользователя не может быть пустым.
2. Телефон должен содержать от 9 до 15 цифр. Допускается знак `+` в начале.
3. Расстояние поездки должно быть положительным числом.
4. Цена не может быть отрицательной.
5. ID пользователей и заказов должны быть уникальными внутри соответствующих списков.
6. Государственный номер автомобиля не может быть пустым или повторяться.
7. Нельзя назначить занятого водителя.
8. Нельзя назначить водителя неподходящей категории.
9. Нельзя начать непринятый заказ.
10. Нельзя повторно завершить поездку.
11. Нельзя удалить пассажира или водителя, если существуют связанные с ним заказы, включая архивные.
12. Нельзя изменять автомобиль водителя во время активного заказа.

Для проверки вводимых значений использовать исключения `ValueError`, `TypeError` и другие по необходимости.

Ошибки должны обрабатываться так, чтобы пользователь возвращался к работе с меню.

## 8. Требования к ООП

Обязательно продемонстрировать следующие темы.

### Классы и объекты

Создать отдельные классы для пользователей, автомобилей, тарифов, заказов и сервиса.

### Инкапсуляция

- Использовать защищённые внутренние атрибуты там, где это оправдано.
- Реализовать `@property`.
- Контролировать изменение состояния водителя.

### Наследование

- `Passenger(User)`
- `Driver(User)`
- `StandardTariff(Tariff)`
- `ComfortTariff(Tariff)`

### Полиморфизм

Метод `calculate_price()` должен работать с объектами разных тарифных классов через общий интерфейс.

Метод `get_info()` должен иметь разные реализации для Passenger и Driver.

### Абстракция

Использовать:

- `ABC`
- `@abstractmethod`

### Декораторы

Применить:

- `@property` — доступ к атрибуту водителя.
- `@staticmethod` — для отдельной вспомогательной проверки данных.
- `@classmethod` — для восстановления объекта из словаря.
- Собственный `@log_action` — для регистрации действий с заказами.

Собственный декоратор должен записывать время выполнения и название действия, например создание, принятие или завершение заказа. Необходимо использовать `functools.wraps`.

### Исключения

Предусмотреть обработку некорректного ввода и недопустимых действий.

### Работа с файлами

Реализовать сохранение и восстановление данных через JSON.

## 9. Сохранение данных

После перезапуска программа должна восстанавливать:

- Пассажиров.
- Водителей.
- Автомобили.
- Заказы.
- Статусы заказов.
- Связи между заказами, пассажирами и водителями.

Для сериализации использовать преобразование объектов в словари и обратно.

При завершении также выполняется сохранение.

Если JSON повреждён, программа должна сообщить об ошибке, не перезаписывая повреждённый файл без предупреждения.

Идентификаторы должны оставаться уникальными после перезапуска.

## 11. Правила архитектуры

1. Каждый файл должен отвечать за свою часть программы.
2. Не размещать всю бизнес-логику в `main.py`.
3. Не дублировать одинаковые функции.
4. Не использовать глобальные списки вместо хранения состояния внутри TaxiService.
5. Не писать огромные методы, выполняющие сразу несколько несвязанных задач.
6. Бизнес-логика должна работать независимо от консольного интерфейса.
7. Для каждого типа тарифа использовать отдельный класс.
8. При работе с заказами обязательно проверять допустимость перехода статусов.
9. Использовать понятные английские имена классов, методов и переменных.
10. Соблюдать PEP 8.
